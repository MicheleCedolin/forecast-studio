# tsfcore: C++ forecasting core

C++17 counterparts of the Python engine's methods, built as one DLL with a plain C interface. Python uses it through
`ctypes` as the `cpp` engine (`--engine cpp`, `src/tsfstudio/engines/cpp_engine.py`). All series of a job go to the library
in one call and are spread over CPU threads inside C++.

## Build
```powershell
winget install BrechtSanders.WinLibs.POSIX.UCRT     # portable GCC + CMake, no admin rights (once)
powershell -ExecutionPolicy Bypass -File cpp\build.ps1
```
Linux (clusters): `bash cpp/build.sh` builds `src/tsfstudio/native/tsfcore.so` with the same flags; see docs/HPC.md for
batch runs and for the agreement checks on Linux.

The DLL is copied to `src/tsfstudio/native/tsfcore.dll` (not in git). It links the GCC runtime statically and depends only on
Windows system DLLs. GitHub Actions builds it with MSVC (`-Generator ""`) for the release package.

## Interface
`tsf_forecast_batch(method, values, offsets, n_series, h, horizons, periods, n_periods, n_threads, out, flags, msg, msg_len)`:
series are concatenated in `values` (series i is `values[offsets[i]:offsets[i+1]]`); `out` is `n_series x h`. A series whose
model fails or returns non-finite values gets the seasonal naive forecast and `flags[i] = 1`, as in the Python engine.
Settings are passed in the method name as `name?key=value&key=value` (`capi.cpp` PMETHODS; validated by `cpp_engine.method_with_params`): holt_winters / holt_ets `error_type` (M = R ets MAM / MAN, checked against R) and `max_season`; dhr_arima `fourier_k` (any K equals R: NN5 weekly K = 1, 2, 3, 5 and daily K = 1, 2, 3 within 1e-6); tsb `alpha_d` / `alpha_p`; dotm / auto_theta `decomposition_type`; auto_ces `model` / `max_season`; auto_mfles `n_windows` / `metric`; (seasonal_)window_average `window_size`; bagged_ets `n_boot` / `seed`; scum `arima_max_season`. The statsforecast ports equal the Python engine with each setting.

## R's svd() and Fourier terms
stats::arima rotates two or more regressors by `svd(xreg)$v`. The sin and cos columns of a Fourier harmonic have equal singular values, so the basis inside that subspace is whatever LAPACK returns and depends on every bit of the input. `lapack_svd.cpp` ports R's path (La.svd -> LAPACK 3.12.1 `dgesdd` JOBZ = 'S': `dgeqr2`, `dgebd2`, `dbdsdc` -> `dlasdq` -> `dbdsqr`, `dormbr`, with the reference BLAS and the LAPACK >= 3.10 `dnrm2`) in the same operation order: `svd(x)$v` and `$d` are bit-identical to R's on 212 test matrices (Fourier with intercept or drift, random; both the QR and the direct path). R's `sin` / `cos` are correctly rounded while the Windows C runtime's are 1 ulp off for about 5% of the Fourier arguments, so `fourier_terms` evaluates them in quad precision (libquadmath, linked statically). Together these took dhr_arima with K = 3 from 7 of 111 NN5 weekly series more than 0.1% away from R to all 111 within 1e-6. Matrices with more than 25 columns (LAPACK's divide and conquer) keep the Jacobi SVD.
