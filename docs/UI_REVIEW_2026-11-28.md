# Forecast Studio UI review, 28 Nov 2026

Scope: the local app (`src/tsfstudio/app/static/*`, `server.py`, `service.py`, `models_info.py`) and the browser edition
(`web/index.html`, `web/app.js`, `web/worker.js`, `web/features.js`, `web/desktop.html`). This follows the review of
22 Nov 2026 (`docs/UI_REVIEW.md`). Items reported as fixed there are only checked here, not repeated.

## How this review was done

- **Local app.** I ran `python -m tsfstudio app --no-browser` with temporary data, runs and uploads folders in the scratchpad.
  The data was the `nn5_weekly` test file only, so 42 of the 43 catalogue entries show "file missing". With Playwright and
  Chromium I did three runs on `nn5_weekly` (Theta, Seasonal naive, ETS; Python engine). I then went through the stale-result
  state, Past runs with the three-run comparison, Series features with the PCA, and dark mode. Widths: 1440×900, 1366×768 and
  390×844 (phone).
- **Browser edition.** A built `web/tsfcore.js` and `web/tsfcore.wasm` were present (untracked, dated 28 Nov 07:38), so I
  served `web/` with `python -m http.server` and ran the page for real: a test run (ETS, 50 series) and a "Forecast the future"
  run, at 1440×900 and 390×844.
- **Screenshots.** Saved in `/tmp/claude-0/-home-user-forecast-studio/668f9be3-e16f-5c7f-b5d4-1d3c578c235a/scratchpad/ui_shots/`.
  Files starting `d…` are the local app on desktop, `p…` the local app on a phone, and `w_…` the browser edition.

## Top 5 changes for look and feel

1. **Make comparing methods a first-class task.** In the local app, allow several models to be selected and run as one batch.
   Add a "Ranking" view (mean rank, a critical-difference chart, a relative-to-benchmark column) that uses the existing
   `tsfstudio rank` code (H1, H2).
2. **Tame the Model step.** 60 models sit in one long radio list (about 12,000 px on a phone). Add search and filter chips,
   a compact layout, and a "Suggested for this dataset" group at the top (H3).
3. **One visual language and one vocabulary for both editions.** Share tokens, number formats and terms. Bring "Forecast the
   future" into the local app and Past runs/comparison into the browser edition (H4, M8).
4. **Polish the charts.** Lighten the horizon band, use real dates on the x-axis, keep labels from colliding, size charts
   correctly when opened from Past runs, and make the readout work with the keyboard and touch (M1, M2, M3).
5. **Fix the small bugs that make the app look unfinished.** All table headers are highlighted as if sorted. The Settings lead
   says "Defaults come from the data file header" for catalogue data. The UI shows "1 warnings", full machine paths and model
   ids instead of names (M4, M5, L-items).

## High

### H1. Methods can only be compared one run at a time
- **Where:** Model step (`app.js:488`, `role="radiogroup"`). Past runs, Comparison (`app.js:1048-1077`).
- **What:** One run means one dataset, one method and one engine. To compare five methods the researcher must select a model,
  wait for the estimate, start the run, wait for it to finish, and repeat, five times. They then go to Past runs and tick five
  boxes. Comparison is limited to a table of means/medians plus one bar chart.
- **Why it matters:** Comparing methods on a dataset is the main research task. At the moment it is the slowest path in the
  app.
- **Change:**
  - Turn the model list into a checkbox list, with the engine choice per row (a small segmented control).
  - Queue the selected models as one "study" job on the server, which already has job/poll/cancel.
  - Show progress as "model 2 of 5, series 40/111".
  - When the study finishes, open the comparison directly.
  - Keep the single-model path as the default for one ticked box.
- **Effort:** L

### H2. No ranking or significance view, although the code exists
- **Where:** Past runs, Comparison (`app.js:1064-1076`). `tsfstudio rank` in `cli.py:599-610` already does Friedman, Nemenyi
  and bootstrap ranking reliability. `web/desktop.html:364` advertises "ranking reliability" for the desktop version, but the UI
  does not offer it.
- **What:** The comparison highlights the lowest mean in yellow. In my test, Theta (SMAPE 0.120) was highlighted against ETS
  (0.121), a difference that is almost certainly noise. There is no mean rank, no relative measure against a benchmark, and no
  indication of ties.
- **Why it matters:** A yellow cell reads as "winner". Researchers will copy that into papers.
- **Change:** When 2 or more comparable runs (same data, horizon and series) are ticked, add a "Ranking" block:
  - A mean-rank column per measure.
  - A "relative to" select (default: Seasonal naive if present) that gives relative MASE/SMAPE, i.e. geometric-mean ratios.
  - With 3 or more runs, a critical-difference chart (Nemenyi) drawn as an SVG axis of mean ranks with bars joining methods
    that are not significantly different. Add the p-value of the Friedman test.
  - Expose it through `/api/rank?runs=…&metric=…` that wraps `ranking.py`.
  - Replace the per-cell "best" fill with bold text plus a small rank number. Use fill only for significant leaders.
- **Effort:** M

### H3. The Model step is a 60-row wall
- **Where:** `app.js:481-504`, `app.css:272-282`. Screenshots `d03_model.png`, `p03_model.png`. The phone page is 16,136 px
  tall, most of it this list.
- **What:**
  - Every model takes 55–90 px on desktop and about 240 px on a phone.
  - There is no search and no filter (by engine, available, intermittent, global).
  - Models that are not installed (14 of 60 here) are mixed with available ones.
  - The "used in the reference study" hint is a small grey italic line. Studied/recommended methods are not grouped.
- **Why it matters:** Choosing a method is the central decision. Scrolling past 60 rows hides the useful ones, and on a phone
  the step is close to unusable.
- **Change:**
  - Add a toolbar like the Data step: search box, and chips "Available only" (on by default), "Py / R / C++", "Suggested for
    this data".
  - Put a "Suggested for nn5_weekly" group at the top, built from `recommended_local`/`recommended_global` and the demand
    profile (for example the Croston family when more than 50 % of series are intermittent).
  - Collapse unavailable models into a `<details>` "14 models need extra packages".
  - Use a compact row (name and badges on one line, summary in the margin note).
  - On phones, hide the summary and keep the name and badges.
- **Effort:** M

### H4. The two editions look and speak like different products
- **Where:** `src/tsfstudio/app/static/app.css:62-114` versus the inline `<style>` in `web/index.html:7-118` and
  `web/desktop.html`. Compare `d06_results_top.png` with `w_desk_results_full.png`.
- **What:**
  - **Look.** The local app uses Latin Modern serif, navy ink, a yellow highlighter, hairline rules and a margin note. The
    browser edition uses system-ui, a blue accent, rounded cards, a gradient top bar and blue step circles. "Download the
    desktop version" leads to an app that looks nothing like the page that sent the user there.
  - **Terms.**

    | Local app | Browser edition |
    |---|---|
    | Measures | Metric |
    | Excluded | Left out |
    | Series features | Data characteristics |
    | Valid series | Series |
    | nRMSE (mean) | nRMSE_Mean |
    | Percent bias | PBias |
    | Results 5-step | Results 4-step |

  - **Numbers.** WAPE shows `11.7%` in one edition and `10.5` in the other. SMAPE shows `0.120` in one and `0.1074` / `0.103`
    in the other (see M4).
- **Why it matters:**
  - Users move between the editions; the docs even send them from one to the other.
  - Inconsistent names and numbers undermine trust in the results.
  - The local app's manuscript style is distinctive and should be the brand.
- **Change:**
  - Extract a shared `tokens.css` (colours, spacing, type scale) and a shared `format.js` (`fmtM`, metric display names,
    units), used by both editions.
  - Bring the browser page closer to the manuscript style: LM fonts (the WOFF files are about 300 kB and can be lazy-loaded),
    navy/yellow accents, rules instead of cards. Alternatively, choose a neutral common style for both.
  - Take metric names and units from `learn.json`, which the browser edition already loads.
- **Effort:** M

### H5. The browser edition loses every result on the next run and cannot cancel
- **Where:** `web/app.js:419-440` (Start), `456-462` (`endRun`), `572-609` (`showResults` replaces `result`).
- **What:**
  - Each run overwrites the previous one, so two methods cannot be compared without downloading the zips and comparing them
    by hand.
  - During a run there is no Cancel; the only way out is to reload the page.
  - "Series to run" defaults to **50** (`index.html:213`). The run therefore covers 50 of 111 series, and this appears only
    in one sentence in the results.
- **Why it matters:** Researchers using the browser page are likely to try 2–4 methods. Silently using a subset makes the
  numbers incomparable with the paper's tables.
- **Change:**
  - Keep a session list of runs: method, n series, summary row. Store it in memory or IndexedDB.
  - Add a small comparison table with the same rank and "relative to" columns as H2.
  - Add a Cancel button that calls `worker.terminate()` and starts a new worker.
  - Show the series limit as a visible chip next to Start ("50 of 111 series, change"). Alternatively, default to all series
    when the dataset is small (the pilot estimate already exists).
- **Effort:** M

## Medium

### M1. Series chart: the horizon band overpowers the data, and the x-axis has no dates
- **Where:** `app.css:333` (`--band-op: .6` on `#ffe45c`), `app.js:935-944` (x labels `t−10`, `cut-off`, `t+8`). Screenshot
  `d07_results_chart.png`.
- **What:**
  - The solid yellow block is the strongest element on the page.
  - The blue dashed forecast sits on yellow with low contrast.
  - The axis shows offsets, not dates. The browser edition shows real dates (`1998-05-18 to 1998-07-06`) using
    `TsfConvert.advance`.
- **Change:**
  - Use a band opacity of about 0.25 (light theme) with a 2 px yellow top rule as the "highlighter" cue.
  - Draw the forecast in solid `--blue` with hollow markers, and keep the dashes for intervals.
  - Compute dates from the series `start_timestamp` and frequency, and show them on hover and on the first/cut-off/last ticks.
- **Effort:** S

### M2. Charts opened from Past runs are drawn at the wrong size on phones
- **Where:** `app.js:922`. `W = max(330, min(780, host.clientWidth - 2))`; when the workspace is hidden, `clientWidth` is 0, so
  W = 780.
- **What:** Past runs, then Open, calls `loadRun` while `#view-work-body` is still hidden. The SVG is built 780 wide and scaled
  to about 357 px, so axis labels become about 5 px (`p08_chart.png`; the histogram has the same problem). The resize handler
  does not fire because the width did not change.
- **Change:**
  - Call `setView("work")` before `loadRun`.
  - Or redraw the chart and histogram in `setView("work")`.
  - Or observe `#chart` with a `ResizeObserver`.
- **Effort:** S

### M3. Histogram and chart text collide and are mouse-only
- **Where:** `app.js:993-994` (mean/median labels at a fixed dy). The browser edition has the same problem in
  `web/app.js:776-860`: in `w_desk_results_full.png` "median 0.7203" is cut off at the bar. Also `app.js:961-968` (readout on
  `mousemove` only).
- **What:**
  - The labels overlap the reference lines and each other ("median 0.8048" is struck through by the mean line in
    `d07_results_chart.png`).
  - On touch screens the readout never appears; there is no `pointer` handling.
- **Change:**
  - Move the mean/median values into a legend line under the chart ("mean 0.885 — median 0.805 ┆").
  - Switch to `pointermove`/`pointerdown` so touch works.
  - Make the SVG focusable with Left/Right moving the crosshair, as the PCA canvas already supports for 3D.
- **Effort:** S

### M4. Number formatting is still inconsistent outside the Results tables
- **Where:**
  - `app.js:855`: `fmt` with 4 significant digits for "Mean forecast / actual".
  - `app.js:1159`, `1174`: the features summary and values show `0.1708`, `0.05674`, `128.8`.
  - `app.js:888`: axis labels.
  - `app.js:854`: bias uses a hyphen-minus, `-3.2%`.
  - `web/app.js:36-43`: 4 significant digits everywhere, and WAPE/MAPE without `%`.
  - `app.js:1164`: "Stored 11/28/2026, 7:42:19 AM" (US locale), while everything else uses ISO `2026-11-28 07:38`.
- **Change:**
  - Use `fmtM` (or a per-column fixed-decimals formatter chosen from the column's magnitude) everywhere.
  - Use a true minus sign (U+2212) for negative numbers.
  - Use ISO dates throughout.
  - Port `fmtM` to the browser edition (part of H4).
- **Effort:** S

### M5. Wrong "defaults" wording for catalogue datasets
- **Where:** `app.js:568` and `571` test `d.kind === "catalog"`, but `service.dataset_detail` returns no `kind` (checked:
  `/api/dataset/nn5_weekly` has no `kind`; `/api/datasets` has `kind: "catalog"`).
- **What:** Settings says "Defaults come from the data file header" and the lag placeholder says "(data)" for nn5_weekly, a
  catalogue dataset whose defaults come from the reference study (`d04_settings.png`). The margin notes still say "The
  original call from your study." (`models_info.py:279` and 7 more).
- **Change:**
  - Add `kind` to the detail payload, or use `entry(S.sel.dataset).kind` in the UI.
  - Replace "your study" with "the reference study".
- **Effort:** S

### M6. Every table header looks "sorted"
- **Where:** `app.css:315` `table.t th[aria-sort] { background: var(--sel-bg); }` matches `aria-sort="none"`, which
  `app.js:1002` sets on every sortable header.
- **What:** In "Errors by series" the whole header row is pale yellow (`d08_results_table.png`), so the user cannot see which
  column is sorted.
- **Change:**
  - Use `th[aria-sort="ascending"], th[aria-sort="descending"]`.
  - Or omit `aria-sort` on unsorted columns, which is also the correct ARIA practice.
- **Effort:** S

### M8. Feature gaps between the editions
- **Where:** `web/index.html:205-208` ("Forecast the future" with 80/95 % intervals, `web/app.js:472-550`) and the
  "Download all (.zip)" button. The local app has neither (no future mode in `service.py`; Files is a list of links,
  `app.js:859-860`).
- **What:**
  - The browser edition can produce an actual forecast beyond the data; the "full" desktop app cannot.
  - The local app has past runs, model settings and Excel output; the browser edition has none of these.
- **Why it matters:** Practitioners want future forecasts; researchers want archives. Each edition currently only half serves
  each group.
- **Change:**
  - Add a "Test a method / Forecast the future" segmented control to the local Settings step, reusing the runner's interval
    code.
  - Add `GET /api/runs/<id>/zip`.
  - Label each file with one line of explanation, as the 22 Nov L11 suggested.
- **Effort:** M

### M9. Progress is still not a progressbar; the browser status is not announced
- **Where:**
  - `app.js:754-758`: `role="status"` block rebuilt each poll, bar `aria-hidden`.
  - `web/index.html:219`: `#status` has no `aria-live`.
  - `web/index.html:221`: `.bar` has no role.
  - The browser results section appears without moving focus.
- **Change:**
  - Render one `<progress max=total value=done>` and update only its value and the text node.
  - Announce stage changes through a separate visually hidden `aria-live="polite"` span.
  - In the browser edition, add `role="status"` to `#status` and `role="progressbar"` with `aria-valuenow` to `.bar`.
  - After a run, move focus to the Results heading (`tabindex=-1`).

## What works well (keep)

- **The manuscript look of the local app.** LM type, navy ink, a yellow highlighter for selection and the forecast horizon, and
  margin notes with checked-citation tags. It is distinctive and calm, and dark mode keeps the metaphor well.
- **The stale-results banner and "Load these settings into the workspace".** Together they make reproduction easy. The "Run
  configuration" block (seed, versions, SHA-256) is exactly what a methods section needs.
- **The browser edition's guidance.** It explains why Start is disabled (`runWhy`). Its "How should an Excel or CSV file
  look?" panel is clear. The interval note ("bounds fell on the wrong side… moved to the forecast") is honest.
- **The PCA map in both editions.** Colouring the map by per-series error, or by the best model per series, is a strong
  research feature. It deserves a more prominent place once H1/H2 exist.
